# System Design: PhishDetect URL Analysis Service (Phase 1)

**Version:** 1.1
**Date:** October 27, 2023
**Status:** Approved

## 1. Executive Summary

This document outlines the architecture and design for the **PhishDetect URL Analysis Service**. The objective of Phase 1 is to develop a robust, scalable, and cost-effective service that analyzes URLs to detect phishing and malicious content.

The project will be built using a **unified, monorepo architecture** with **Next.js**. The backend logic will be implemented as **Next.js API Routes** and deployed as serverless functions on **Vercel**. This approach simplifies the development workflow, consolidates the codebase, and leverages Vercel's generous free tier for hosting. A **Supabase PostgreSQL** instance will be used for persistent caching of analysis results.

## 2. Goals and Requirements

### 2.1. Functional Requirements
- **F-1: URL Input:** Users must be able to submit a single, valid URL for analysis.
- **F-2: Analysis Engine:** The system must orchestrate calls to multiple external APIs (Google Safe Browsing, VirusTotal, PhishTank) to gather threat intelligence.
- **F-3: Clear Verdict:** The system must provide a simple, conclusive verdict for each analysis (e.g., "Safe," "Suspicious," "Malicious").
- **F-4: Detailed Reporting:** The UI must display the individual results from each external service to provide transparency.
- **F-5: Result Caching:** To optimize performance and cost, all analysis results must be cached in the database.

### 2.2. Non-Functional Requirements
- **NF-1: Performance:** API response time for cached results should be < 500ms. For uncached results, it should be < 3 seconds under normal conditions.
- **NF-2: Reliability:** The system must be resilient. Failure of one external API should not prevent the system from returning a verdict based on the remaining services.
- **NF-3: Scalability:** The serverless architecture will automatically scale with demand.
- **NF-4: Security:** All communication must be over HTTPS. Basic input sanitization must be performed on all user submissions.
- **NF-5: Cost-Effectiveness:** The system must be designed to operate within the free tiers of Vercel, Supabase, and all external services during initial stages.

## 4. Database Schema

- **Provider:** Supabase
- **Table Name:** `url_analysis_cache`
- **Purpose:** To store the final, aggregated results of URL analyses.
- **SQL Definition:**
```sql
CREATE TABLE url_analysis_cache (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  created_at TIMESTAMPTZ WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL,
  url TEXT NOT NULL UNIQUE,
  final_verdict TEXT NOT NULL, -- e.g., 'Safe', 'Suspicious', 'Malicious'
  full_report JSONB NOT NULL,
  last_scanned_at TIMESTAMTz WITH TIME ZONE NOT NULL
);

-- Create an index on the URL for fast lookups
CREATE INDEX idx_url ON url_analysis_cache(url);
```

## 5. API Endpoint Definition

The API will be implemented as a Next.js API Route.

- **Endpoint:** `POST /api/v1/analyze` (File path: `/pages/api/v1/analyze.ts`)
- **Request Body:**
  ```json
  {
    "url": "https://example.com"
  }
  ```
- **Success Response (200 OK):**
  ```json
  {
    "url": "https://example.com",
    "verdict": "Safe",
    "confidenceScore": 98,
    "scannedAt": "2023-10-27T10:00:00Z",
    "source": "cache" | "live",
    "report": {
      "googleSafeBrowsing": { "isMalicious": false },
      "virusTotal": { "positives": 0, "total": 90 },
      "phishTank": { "isKnownPhish": false }
    }
  }
  ```
- **Error Responses:**
    - `400 Bad Request`: For invalid or missing `url`.
    - `500 Internal Server Error`: For server-side failures.
